# 13 — 三张 UI Kit 正式裁定（VISUAL RULING v1）

> 状态：`生效`（用户 2026-10-04 正式裁定）｜维护者 DSH
> 本文件把用户对 **MAIN_MENU / PREPARATION / COMBAT** 三张 UI Kit 的**第一版正式视觉方向**固化为可执行硬约束。
> 用户原文（28 节）见 PET-37 该条评论；**冲突时以用户原文为准**，本文件是可执行摘要。

## 0. 裁定结论

三张 Kit：**有条件批准（APPROVED WITH MINOR REVISIONS）**。方向正确，**不必因视觉稿暂停开发**。

| 界面 | 结论 |
|---|---|
| **PREPARATION** | **通过** —— 三张中优先级最高，**优先进 Godot** |
| **MAIN_MENU** | **通过，小改后接入** |
| **COMBAT** | **通过，但先完成一轮信息层级整理，再正式接入** |

## 1. 视觉核心（正式）

**蓝图 · 节点 · 机械装置 · 战斗机器 · 武器 · 敌人 · 自动战斗 · 浮空岛 / 工坊世界 · 日式Q版像素风 UI。**

「日式Q版像素风」= 比例可爱 · 图形简洁 · 像素轮廓明确 · 色彩明快 · 武器与机械 Q 版化 · 敌人可读且有一定可爱感 · UI 精致但不繁杂。
**不等于必须出现人物角色。**

## 2. 角色与吉祥物（硬约束）

- 当前阶段**不确立固定主角**；**不确立** 工坊少女 / 猫咪 / 吉祥物 / 引导角色 为必需设定。
- 参考图里出现的人物或猫咪**只是构图元素**，**不得**据此推导出「游戏必须有角色陪伴系统」。
- **不得擅自增加**：主角设定 · 猫咪吉祥物 · 陪伴系统 · 对话角色 · 剧情角色 —— 除非用户以后主动决定加入。
- **MAIN_MENU**：可保留角色/物件摆放空间，但**不强制放人物**；可用 工坊设备 / 蓝图桌 / 核心机器 / 浮岛景观 / 武器展示 / 机械装置 填充。
- **PREPARATION**：**不需要人物**占据蓝图界面空间；**蓝图工作台是绝对视觉中心**。
- **COMBAT**：玩家方可直接表现为 核心装置 / 基地 / 武器平台 / 机器系统，**不要求可操作人物**。
- **FIRST PLAYABLE**：**暂不制作正式主角**，优先验证「**机器构筑本身是否有趣**」。

## 3. MAIN_MENU（通过，小改后接入）

**保留**：16:9 横屏 · 左右空间分区 · 中央主菜单 · START 主按钮 · CONTINUE · SETTINGS · EXIT · 深蓝 UI · 暖金高亮 · 木质/黄铜辅助色 · 像素描边风格。

小改四项：

1. **Logo 区强化**：建立清晰的游戏 Logo 区（`PixelFusion` 或 `PixelFusion / 像素融合屋`）。
   **不要**大量特效、巨型宣传式 Logo、占满界面 —— Logo 的职责是**品牌识别**，不是广告展示。
2. **左侧不强制人物**：构图区可保留；未来允许替换为 蓝图工坊 / 核心机器 / 工作台 / 武器装置 / 浮岛窗口 / 机械设备。
   **不得**因为参考图出现少女就擅自建立正式女主角。
3. **右下信息框弱化**：当前 `MENU PANEL` 更像开发说明框。正式版**要么删除**，要么改成 版本号 / 简单提示 / 当前存档信息 等**非主要辅助信息**；**不得形成新的视觉中心**。
4. **按钮状态规范**：必须建立 **Normal / Hover / Focus / Pressed / Disabled** 五态。
   PC：Hover 与 Focus 可区分；手柄/键盘：**Focus 必须清晰**；触摸：**Pressed 必须明确**。

## 4. PREPARATION（通过 · 最高优先级）

信息架构**正式通过**：左侧关卡信息 · 中部蓝图工作区 · 右侧节点详情 · 底部节点仓库 · 右下「开始战斗」。

- **蓝图区是页面第一视觉重点，面积必须最大**；**不得为装饰压缩蓝图区**。
- 必须体现「**这是一个可以操作的工作台**」：`Grid` / `Slot` / `Node` / `Port` / `Connection` / `Selected` / `Valid placement` / `Invalid placement`。
- **节点卡**：`CORE`（核心节点）/ `FUNCTION`（规则节点，如 Split / Amplify / Delay）/ `WEAPON`（武器节点）三类须**快速可辨**。
  未来若加 `CONTROL` / `SPECIAL` 再建分类；FIRST PLAYABLE **不必一次做全**。
- **节点颜色不能乱**：类型只通过 图标 / 边框 / **小型分类色** 辅助识别；
  **禁止**整张卡片用大量高饱和颜色做类别区分，整体仍以统一深蓝 UI 为基础 —— **不能把界面做成彩虹色**。
- **Detail 面板字段**：节点图标 · 名称 · 类型 · 简短作用说明 · `Energy` · `Heat` · 核心参数 · 特殊效果。
  **不要把全部数学公式塞进去**；详细公式放 Tooltip 或高级说明。
- **节点仓库**：`N1~N8` 占位可继续用于开发；正式版显示 图标 / 名称 / 类型 / 数量或可用状态；
  **不要在节点卡上放太多文字**，优先「一眼认出是什么节点」。
- **START 按钮**：正式文本「**开始战斗**」；它是本页**唯一主要行为**，视觉权重**高于** 清空 / 保存 / 详情 / 分类 等辅助操作。

## 5. COMBAT（通过，先整理信息层级）

主要问题**不是风格错误，而是各区域视觉权重太平均**。

- **顶部 HUD 分层**：**一级** = `CORE / HP` · `HEAT` · `WAVE`；**二级** = `GOLD` · `NEXT`（视觉可稍弱）。
  **不要让五块 HUD 像五个同等级菜单按钮。**
- **战斗区是第一视觉中心**：第一眼应看到 玩家基地/核心 · 敌人 · 弹丸 · 武器行为 · 战斗反馈，**而不是先看到 HUD**。
- **玩家方表现**：`Core` / `Base` / `Machine` / `Weapon platform` / 蓝图生成的装置 —— **不要求人物**。
- **敌人方向**：保持日式Q版像素风；**轮廓清楚 · 尺寸区别 · 行为可识别 · 细节不过量**。
  `Slime` / `Runner` / `Tank` 应**一眼看出行为差异**。
- **战斗特效规则**：不追求满屏爆炸。FIRST PLAYABLE 优先保证玩家能看清
  「**哪把武器发动 → 攻击谁 → 造成什么结果**」。少量 命中闪光 / 轻微爆炸 / 弹道 / 击退 / 状态提示 即可；
  **不得**为「爽」提前堆 巨量粒子 / 全屏闪光 / 大面积特效 / 大量伤害数字。
- **Machine 面板（左下）**：承担**机器运行状态反馈** —— 当前 Heat · Energy · Active Chain · 最近触发模块
  （如 `CORE → SPLIT → BOMB`）。**不需要一次显示整个 Blueprint。**
- **底部区域重新定义**：**禁止**把 机器/武器 与 敌人（Slime / Runner）混在同一栏。
  底栏**只承担当前机器 / 武器运行信息**（Needle / Bomb / Saw：是否 Active · CD · Energy · Heat）；
  **敌人信息应出现在战场或 NEXT 面板**。
- **NEXT 面板**：用于下一波预览，保持简洁（`Slime ×3` / `Runner ×1`）；**不要变成敌人图鉴**。

## 6. 三屏统一 + 颜色

- 三张 UI 必须使用**同一套** Panel / Border / Button / Font / Shadow / Gold highlight / Navy background / Brown secondary / Icon style / Spacing。
  **禁止三个页面分别做三套 UI。**
- 当前正式颜色方向（现有设计 Token）：`NAVY` · `BLUE` · `GOLD` · `BROWN` · `RED` · `ORANGE` · `GREY` · `WHITE`。
- **任何正式色值仍必须通过 `palette.tres` 统一管理；禁止在 GDScript 中随意硬编码颜色。**

## 7. 分工与阶段（用户裁定）

- **Codex → 组件化制作阶段**：**不需要重新制作三张大稿**。优先拆
  `Panel` · `Button` · `Node Card` · `Inventory Slot` · `HUD Block` · `Tooltip` · `Progress Bar` · `Frame` · `Selected State` · `Disabled State`；
  **先给用户看关键组件预览**，批准后再批量产正式资源。
- **Claude → 不等美术**：立刻按当前 Kit 建立 Godot UI 场景结构；资源未批准前**继续使用 placeholder**，批准后**逐个替换**。
- **优先级**：`FIRST PLAYABLE > UI 细节打磨 > 大量正式美术`。
  **不得**因为一个边框 / 一个图标 / 一个色差 / 一个按钮 **再次阻塞玩法开发**。
