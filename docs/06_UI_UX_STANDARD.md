# 06 — UI / UX 规范（UI & UX STANDARD）

> 状态：`FROZEN-DRAFT`（待用户批准）｜版本 **v0.1.9**｜维护者 DSH（协同 Codex Visual Reviewer）
> 本文件是 UI 实现的验收依据。所有数值为逻辑像素（基于 320×180 基准，双端整数倍缩放）。

## 1. 全局

| 项 | 规定 |
|---|---|
| 基准分辨率 | 320 × 180（16:9），整数倍缩放 |
| 安全区 | 四周内缩 8px；手机端额外汇总刘海/手势区，实际可用区由 `SafeArea` 容器统一处理 |
| 间距系统 | 4 / 8 / 12 / 16 / 24（只用这五个值，禁止 5、7、13 这类随手值） |
| 描边 | 统一 1px（清晰态）；禁止 0.5px、1.5px |
| 面板角 | 像素角（直角），圆角一律禁用抗锯齿圆角 |
| 阴影 | 仅允许 1px 偏移硬阴影，禁止模糊阴影 |
| 字体 | 中文像素字体（待 Codex 选定并经用户批准）；正文 ≥ 8px，标题 ≥ 12px |
| 触摸命中 | 最小 **44×44 设备像素（物理）** = 2× 缩放下 22 逻辑像素、4× 下 11 逻辑像素。**不是 320×180 逻辑像素** —— v0.1.2 写成「44×44 px（逻辑像素，按缩放换算）」自相矛盾，已改（Codex 审查指出）|
| 最小缩放 | 触摸平台 **≥ 2×**（640×360）；桌面 ≥ 2×。保证最小交互元素（24 逻辑像素）≥ 44 设备像素 |

## 2. Panel（含装饰外框 —— v0.1.3 升为一等规格）

参考图的 UI **不是**「纯深蓝扁平面板」。Codex 目视 A/B/C 的结论是：
**暖木 / 黄铜厚外框包住深蓝内芯，再点缀小面积亮金高光**。
这一条与 DSH 的独立实测**互相印证** —— 构成图显示画面左缘（x 0–5%）与底缘（y 97–100%）确为暖色木质带。

### 2.1 三层结构（强制）

| 层 | 内容 | Token |
|---|---|---|
| **外框**（decorative frame） | 木质/黄铜厚边、转角、铆钉 | **填充 `BROWN_600` / 描边 `BROWN_500`**（v0.1.4 由 Codex 裁定）；转角与铆钉 `GOLD_600` / `GOLD_500`；最亮边 `GOLD_200` |
| **内芯**（content core） | 真正承载内容的面 | `NAVY_800`（主）/ `NAVY_700`（抬升） |
| **高光** | 1px 内高光、选中辉光 | `GOLD_200`（暖高光）/ `BLUE_300`（激活）。**本层必须有可被场景引用的落点**（v0.1.4）：S1-05 前由 Theme 提供；Codex 出正式外框素材后，静态 1px 内高光可移交素材，但「选中辉光」`BLUE_300` 必须始终留在 Theme。**边数（v0.1.6，Codex 裁定）**：`GOLD_200` 静态内高光**仅上边 + 左边**（材质受光，与 `05 §3`「光源方向统一为左上」一致，**禁止四边整圈**）；`BLUE_300` 选中辉光**四边整圈**（交互状态需包围式轮廓，密集蓝图网格上才读得稳）。两者**不得共用同一套边数**。 |

### 2.2 尺寸

| 属性 | 主面板框 | 次级面板（面板内卡片） |
|---|---|---|
| 外框厚度 | **3px** | **1px** `BROWN_600` |
| 内描边 | 内芯外沿 1px `NAVY_600` | 无 |
| 内边距 | 12px | 8px |
| 标题栏高度 | 16px | — |
| 标题栏底色 | `NAVY_700` + 1px 底部 `GOLD_600` 分隔线 | — |
| 阴影 | 右下 1px `NAVY_900` 硬阴影（**不模糊**） | 同 |

**禁止**：模糊阴影、抗锯齿圆角、**没有外框的裸深蓝面板** —— 那正是「纯深蓝扁平 UI」，会丢掉参考图的核心层次。

#### 读数澄清（v0.1.8，Codex 裁定，2026-10-03）

§2.2 的三处读数在 S1-06 实现时产生歧义，由 Codex 依参考图与本节语义裁定。
**三项裁定均确认当前实现无需改动**（Claude 的解读正确）：

| # | 歧义 | 裁定 | 唯一语义来源 |
|---|---|---|---|
| ① | 标题栏「16px」是否**包含**底部 1px 金线 | **包含** —— 总高 16px，金线占第 16 像素行。理由：本节把「高度」列为尺寸、把「底色 + 底部分隔线」列为视觉构成；`StyleBoxFlat` 描边画在矩形**内侧**，正好同时守住 16px 与 1px 两条 | `PaletteTheme.TITLE_BAR_HEIGHT` |
| ② | 内容缩进「12px」从**哪里**量起 | 从**内芯外沿**量起 —— 故从主面板矩形读数是 `3px 外框 + 12px = 15px`。理由：§2.1 已把外框与内芯分层，内容应落在真正承载内容的内芯里，而不是压进装饰外框 | `PaletteTheme.FRAME_BORDER_WIDTH + PaletteTheme.PANEL_CONTENT_MARGIN` |
| ③ | `.tscn` 里 offset 只能是字面量 | **允许** —— Godot 场景格式限制；但**必须由测试拿常量公式核对**，防止规格漂移 | 同上公式，测试对其断言 |

> **联动修改规则**：将来若改 ① 或 ②，必须把**常量、`.tscn` 字面量、测试期望三处一起改**；
> 三者中任何一个单独改动，都应让像素探针报红。这是本澄清能被机器守住的关键。


**阴影的实现方式（v0.1.5 实测裁定）**：`StyleBoxFlat.border_color` 是**单值**、四边共用，
而本节已把三个面板 stylebox 的描边色占满（外框 `BROWN_500` / 内芯 `NAVY_600` / 次级 `BROWN_600`），
故 `NAVY_900` 的右下硬边**无法与面板自身的描边共存于同一条 stylebox**。
裁定采用 **(甲) 场景组合**：用一条独立的 `PanelShadow` 叠层（`draw_center = false`、
`border_width_right/bottom = 1`、`expand_margin_right/bottom = 1`）由场景叠在最外，**面板自身不带阴影**。
**否决 (乙)**「让外框自己承担、右下各多 1px `BROWN`」：那会改掉本节指定的 `NAVY_900`，
且 `BROWN` 深边压在 `BROWN` 外框上根本读不出阴影。
接线属 S1-05（`scenes/**`）；实测依据 `tests/unit/run_render_probes.gd`（聚合入口，见 `09_TEST_STANDARD.md` §4）。

> ⚠ `StyleBoxFlat.shadow_*` **不可用**（v0.1.5 像素级实测）：`shadow_size = 0` 时**一个阴影像素都不画**，
> 且 `shadow_offset` 同时失效；`shadow_size > 0` 则必然带出与 `shadow_size` 等宽的半透明羽化带。
> 引擎只暴露 `shadow_color` / `shadow_size` / `shadow_offset`，**没有关闭羽化的开关** ——
> 「有没有阴影」与「羽化多宽」不可解耦。三个渲染后端（`gl_compatibility` / `forward_plus` / `mobile`）结果一致。

> 上表数值为**规范定义值**（不是从参考图量出来的）—— 外框厚度与铆钉节奏属于手工重绘时的设计决定，
> 须在 Stage 1 由 Codex 出正式 UI 素材时校准；但「**必须有外框**」这一条是硬约束。

## 3. Button — 五种状态（强制）

| 状态 | 底色 | 描边 | 文字 | 说明 |
|---|---|---|---|---|
| `Normal` | `GOLD_500` | `GOLD_600` | `NAVY_900` | 默认 |
| `Hover` | `GOLD_400` | `GOLD_500` | `NAVY_900` | 鼠标/触摸悬停，允许 1px 上移 |
| `Pressed` | `GOLD_600` | `GOLD_600` | `NAVY_900` | 按下，下移 1px |
| `Disabled` | **`NAVY_800`** | `NAVY_600` | `GREY_500` | 不可用 —— 底色必须是 `NAVY_800`：`GREY_500` 在 `NAVY_700` 上仅 3.84:1（不达标），在 `NAVY_800` 上为 4.80:1（达标）。见 `04_COLOR_SYSTEM.md` §5.1 |
| `Selected` | `GOLD_400` | `BLUE_400` | `NAVY_900` | 当前选中项，外框 1px 蓝色 |

辅助按钮（次要操作）：底色 `NAVY_700`，描边 `NAVY_600`，文字 `GREY_300`。

**禁止**：用红色做普通按钮（红色只属于 HP/危险/伤害/警告）。

## 4. Node Card（蓝图节点卡）—— v0.1.3 依实测重设尺寸

**尺寸依据**：对 Reference B 中心蓝图区做**自相关周期测量**，得到节点间距 **≈22–26 逻辑像素**（方法见 §12.2）。

v0.1.2 写的 **48×48 大于实测值的两倍** —— 128px 宽的工作区只能放下 2 列多，
而参考图可见 5–6 列。这是本轮最重要的修正：Codex 由目视提出，DSH 由测量独立确认。

| 属性 | v0.1.3 | 说明 |
|---|---|---|
| 网格间距 | **24 逻辑像素** | 实测 22–26 区间取整 |
| 卡片尺寸 | **24 × 24**（含 1px 描边） | 选中时外框 1px `BLUE_400` |
| 图标区 | 16 × 16，居中 | |
| 类型标识 | **4×4** 色块（左上）：CORE=`GOLD_400`、FUNCTION=`BLUE_400`、WEAPON=`ORANGE_500` | |
| 稀有度 | **3×3** 菱形（右下）：普通=无、罕见=`BLUE_300`、稀有=`GOLD_400`（**不得**用红色） | |
| 连接接口 | **3×3**，输入在左/上，输出在右/下；未连接时低频描边闪烁（≤1Hz） | |
| **名称** | **不显示在卡片上** | 24px 放不下可读中文 —— 名称改由 **Tooltip** 与**右侧节点详情面板**承载 |
| 拖动 | 拖拽时半透明 70%，吸附到 24px 网格 | |

- 卡片底色 `NAVY_700`，外框 1px `BROWN_600`（次级面板框，见 §2.2）。
- 24 逻辑像素在 2× 缩放下 = **48 设备像素**，4× 下 = 96，**均 ≥ 44 设备像素触摸下限**（见 §1）。
- 底部仓库槽位同样取 **24×24，间距 28px**。

## 7. 布局：PREPARATION（Reference B）

**完整蓝图构筑阶段。** 时间停止、无敌人、不战斗、不发射、不扣血。

区域结构由用户指令固定为 **左 / 中 / 右 / 下 / 右下** 五区。下列像素值为对 Reference B 的**实测反推**（方法见 §12），基准 320×180：

```
┌────────────┬────────────────────┬──────────────┐
│ 左：关卡信息 │  中：蓝图工作区     │  右：节点详情 │
│ x 15–88    │    x 98–226        │  x 226–309   │
│ (≈73px)    │    (≈128px)        │   (≈83px)    │
├────────────┴────────────────────┴──────────────┤
│ 下：节点仓库（高 48px，y 132–180）                 │
│                                   ┌──────────┐ │
│                                   │ 开始战斗  │ │
│                                   │x246–310  │ │
│                                   │y148–162  │ │
│                                   └──────────┘ │
└────────────────────────────────────────────────┘
```

**实测依据**（Reference B，1672×941 归一到 320×180）：

- 竖直分栏边界出现在 **x ≈ 27.6%** 与 **x ≈ 70.6%**（边界强度为全图最高的 65.7% / 97.6%）。
- 左栏 **x ≈ 4.7%–27.6%** → **15–88px（宽 ≈73px）**；27.6%–30.7% 为分隔槽；中栏 **x ≈ 30.7%–70.6%** → **98–226px（宽 ≈128px）**；右栏 **x ≈ 70.6%–96.7%** → **226–309px（宽 ≈83px）**。
- **「开始战斗」CTA 是一块亮色区块，实测位于 x ≈ 77%–97%、y ≈ 82%–90%**（≈64×14px）→ 确认在**右下角**，与本规范一致。
- 画面外侧有一圈暖色木质外框（左 ~0–5%、底部 ~97–100%）。

**底部仓库条高度 = 48px（y 132–180）**。

该值经历过一次修正，过程记录在此以免后人困惑：

1. v0.1.2 曾定为 64px，理由是「Node Card 合计 58px（48+2+8）装不进 48px」。
2. v0.1.3 把 Node Card 改为实测的 **24×24**（§4），且**名称不再占卡片高度**（改由 Tooltip / 详情面板承载），
   于是 58px 这个约束**消失了** —— 64px 的理由随之失效。
3. 24px 槽位 + 上下留白 → **48px** 足够，且与实测 CTA 位置（y 148–162，居中于 132–180）自洽。

> ⚠ 边界检测**未能单独切出**这条横带的上下边（它与中/右栏底部像素相连）。
> 48px 是**由槽位尺寸 + CTA 位置推导**出来的值，不是直接量出来的 —— 须在 Stage 1 对照 Reference B 复核。

- 主区域必须全部服务于蓝图配置，禁止放置与构筑无关的装饰面板。
- 「开始战斗」按钮必须是右下角最显著的唯一主动作按钮。

### 7.1 移动端折叠规则（v0.1.2 新增，Codex 审查提出）

320×180 基准下的三栏（≈73 / ≈128 / ≈83px）在手机上**不可能**原样呈现 —— 触摸命中下限就有 44px。
因此竖屏 / 窄屏必须折叠：

| 区域 | 窄屏行为 |
|---|---|
| 左：关卡信息 | 默认**收起**为顶部一条 16px 信息条，点击展开为覆盖层 |
| 中：蓝图工作区 | **始终保留**为唯一常驻主区域 |
| 右：节点详情 | 由侧栏改为**底部弹层**，选中节点时弹出，点空白处收起 |
| 下：节点仓库 | 保留为底部条，改为**横向滚动** |
| 右下：开始战斗 | 固定在右下角安全区内，**始终可见**，尺寸不小于 44×44 |

双端一致性要求：折叠只改变**布局**，不改变任何玩法规则与状态流。

### 7.2 读数澄清（v0.1.9，Codex 裁定，2026-10-03）

S1-07 实现时上报了 5 项 §7 / §7.1 的读数与几何问题。Codex 逐项裁定如下。
**结论：代码现状保留，只修文档。**

**① CTA —— `64×14` 是「参考图亮色区块」的读数，不是 Button 控件的最终矩形。**
- `RegionAction` 保持 `Rect2(246, 148, 64, 14)`（这是实测反推的**区块**读数，测试逐值断言）。
- 「开始战斗」是一个**中文 Button**，其**最小高度为 20px**（14px 装不下中文字），
  故实机矩形为 **`x 246–310 / y 142–162`** —— **x 跨度照抄、右下角 (310,162) 照抄，高度向上扩展**。
- **禁止**为了让按钮压回 14px 而缩小字号或更换更短的文案。
- ⚠️ 若本节只写 `64×14` 而不区分「亮色区块」与「Button 控件」，后续实现者会**再次**把按钮压到装不下中文的高度 ——
  这条消歧必须留在正文，不能只活在评论里。

**② 三栏顶边 `y = 8`**：确认。三栏为 `Rect2(15,8,73,124)` / `Rect2(98,8,128,124)` / `Rect2(226,8,83,124)`
（顶边取自 §1 冻结的 8px 安全区，向下延伸到底条顶边 `y=132`）。

**③ 窄屏底部弹层高度**：确认取**视口高度的 1/3**（§7.1 只定行为、未定高度，此处补定为 1/3）。

**④ CTA 与底条右边缘的 1px 外溢**：CTA 区块 `x` 到 **310**，而底条右边 `x = 309` ——
**两组都是实测事实，都不得为「对齐」而改动**。
CTA 覆盖底条右边框的部分**按实机画面认定为遮挡**（像素探针扣掉被覆盖的行，不断言整条边可见）。

**⑤ 铺满屏幕的 PREPARATION 外壳不补 `PanelShadow`**：`PanelShadow` 是「浮动面板右下硬阴影」的场景组合方案（§2.2）；
铺到视口边缘的外壳没有可读的右下偏移空间，参考图也不是一张浮起的整屏卡片。
主菜单的 `MenuPanel` 是**浮动面板**所以有 Shadow —— **整屏外壳不照搬这一条**。

## 8. 布局：COMBAT（Reference C）

- 进入 COMBAT 后，**蓝图主界面消失**，战斗画面占据整个主区域。
- 敌人生成、推进、CORE 运行、武器执行、Heat 计算全部可见、可读。
- 玩家主要职责是**观察机器的运行结果**，因此信息密度优先于特效。
- HUD 贴边，不遮挡战场。

**实测依据**（Reference C，1672×941 归一到 320×180）：

- **战场主区：y ≈ 0%–75%** → 320×180 下约 **y 0–135**。
- **底部有一条横贯全宽的深色条：y ≈ 75%–100%** → 约 **y 135–180，高 ≈45px**（占画面高约 25%）。
  该带内几乎全部是海军蓝系像素，判定为 HUD 条。
- 画面顶部有天空蓝透过（浮空岛背景）；左侧有一条暖色/深色竖边。

**据此规定**：COMBAT 底部 HUD 条高度取实测值 **≈45px（y 135–180）**，全宽，底色 `NAVY_800`，上沿 1px `NAVY_600` 分隔。

**这条带的性质**（Codex 审查提出，采纳）：它**不是**「贴边小条」，而是一条**底部命令带 / 队列带**。
结合本项目的核心体验 —— 「玩家在 COMBAT 阶段的职责是**观察**机器的运行结果」—— 这条带里的卡片应以
**状态展示与预览**为主（当前波次、CORE 状态、Heat/Energy、待发射队列），
**不得**被做成需要玩家实时点选的动作栏 —— 那会在 COMBAT 引入即时操作，违反 `00_PROJECT_CHARTER.md` §5 交互硬规则第 3 条。

> ⚠ 实测的 25% 画面高比「贴边小条」的直觉更大 —— 这是参考图的事实。
> 若你想让它更紧凑（例如 24–32px），那属于**整体视觉方向的调整（GATE 3）**，需你确认后才改。

## 9. 布局：REWARD

## 10. 交互硬规则（违反即打回）

1. 进入 PREPARATION 后**永远等待玩家**；禁止自动倒计时、自动开怪、自动开波。
2. `PREPARATION → COMBAT` **只能**由点击「开始战斗」触发。
3. COMBAT 期间不得弹出需要玩家即时反应的模态窗口。
4. 任何破坏性操作（删除节点、重置蓝图）必须二次确认或可撤销（Ctrl+Z / 触摸撤销按钮）。
5. 禁止 UI 直接修改战斗内部状态。
6. 所有交互必须同时支持鼠标与触摸。
7. 禁止在场景文件中硬编码颜色，必须走 Theme + Palette。

## 11. 可读性 / 无障碍

- 正文对比度 ≥ 4.5:1，标题 ≥ 3:1。
- 不得用颜色作为唯一状态区分手段。
- 必须支持「减少动态效果」开关：关闭流光、震动、闪烁。

## 12. 参考图实测布局证据（2026-10-03）

本节记录 §6 / §7 / §8 中布局数值的来源，避免它们被误当作「设计出来的」而非「量出来的」。

**方法**（纯标准库，无第三方依赖，可复跑）：

1. 对三张参考图做完整 PNG 解码（zlib + 逐行反滤波），得到 1672×941 RGB 原始像素。
2. **边界检测**：按列/按行统计相邻像素亮度差的均值，平滑后取局部极大值 → 得到面板竖向/横向边界的位置与强度。
3. **构成图**：把画面降采样为 78×40 的网格，每格取众数颜色类别
   （`#` 深海军蓝 / `~` 天空蓝 / `o` 亮白 / `w` 暖色 / `.` 其他），以 ASCII 输出 —— 用于在不依赖图像输入的前提下判读构图。
4. 脚本：`tools/ref_layout_probe.py`（边界检测）与 `tools/ref_compose_map.py`（构成图）。两者均为纯标准库、可复跑。

**结论可信度**：

| 结论 | 可信度 |
|---|---|
| PREPARATION 三分栏边界 x ≈ 28% / 68% | **高**（边界强度全图最高） |
| PREPARATION 的 CTA 位于右下角 x 77–97% / y 82–90% | **高**（与取色结果 `#F0C060` 独立吻合） |
| COMBAT 底部有全宽深色 HUD 条 y ≈ 75%–100% | **高**（该带几乎全为海军蓝） |
| MAIN_MENU 左暖色 / 中亮色 UI / 右天空蓝 | 中（构成图可读，但无法定位到具体控件） |
| 各区域的**精确**像素边界 | 低（插画有渐变与柔边，边界天然模糊） |

**因此**：本文件中的布局数值凡标注「实测」的，都允许在 Stage 1 对照真图微调；凡标注「暂定」的，必须在 Stage 1 确认后才能固化为冻结值。

### 12.2 节点/槽位间距的自相关测量（v0.1.3 新增）

§4 的 24px 从何而来 —— 记录方法以便复算：

1. 取 Reference B，锁定中心蓝图区（图像 x 513–1180）与底部仓库带（图像 y 640–900）。
2. 计算逐列亮度梯度（边界强度），得到一维信号。
3. 对该信号**去均值后做自相关**，在 lag 8–170 图像像素范围内找峰值。

**结果**（1 逻辑像素 = 5.225 图像像素）：

| 区域 | 最强周期 | 折合逻辑像素 | 自相关强度 |
|---|---|---|---|
| 底部仓库带 | 118 px | **22.6** | 25.54（该区最强） |
| 中心蓝图区 | 136 px | **26.0** | 7.87 |
| 中心蓝图区 | 92 px | 17.6 | 7.65 |

→ 节点/槽位间距落在 **22–26 逻辑像素**，取整为 **24**。
→ 128px 宽的工作区因此可容纳 **约 5 列**，与参考图目视的 5–6 列一致；**48px 只能放 2 列**，明显不符。

**置信度：中高。** 自相关给出的是周期而非绝对尺寸，且插画有柔边会把周期略微模糊；
但 22.6 与 26.0 来自两个独立区域且互相接近，又都与「48px 差一倍以上」这一结论一致 —— 足以推翻 48px。
