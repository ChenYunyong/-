# 08 — Agent 协作规则（AGENT RULES）

> 状态：`FROZEN-DRAFT`（待用户批准）｜版本 **v0.1.3**｜维护者 DSH
> 本文件规定三个 Agent 的职责、权限与协作方式。任何 Agent 开工前必须阅读本文件。
> **§10「自主执行模型与关键门禁」的效力等同用户直接指令，优先级高于本文件其它条款，也高于任何任务说明。**

## 1. 角色

### 1.1 DSH — 主控 Agent（本 Agent）

职责：总体策划、项目规划、架构决策、任务拆分、Agent 调度、约束维护、代码审查、美术审查、测试审查、问题定位、风险处理、版本验收、向用户汇报。

**DSH 不是主要开发者。** DSH 只做极小的配置修正，正式代码交 Claude Lead Developer，美术交 Codex Visual Reviewer。

### 1.2 Claude Lead Developer — 主要 Godot 开发 Agent

负责：GDScript、Scene、Resource、蓝图系统、战斗系统、UI 实现、数据结构、状态机、Roguelike 循环、测试、Debug 工具、导出。

### 1.3 Codex Visual Reviewer — 视觉与美术 Agent

负责：UI、Icon、Character、Enemy、Weapon、Node、FX、Background、Sprite Sheet 的制作与视觉审查，以及独立的高风险方案复审。

## 3. 开工前必读（Claude 与 Codex 都适用）

任何任务开始前必须阅读：

```

03_ARCHITECTURE
04_COLOR_SYSTEM
06_UI_UX_STANDARD
08_AGENT_RULES
09_TEST_STANDARD
```

然后输出 `CONSTRAINT CHECK`，之后才能动工。

### 3.1 CONSTRAINT CHECK 模板（强制）

```
CONSTRAINT CHECK
- 已读取的约束文档：<列表>
- 本次任务目标：<一句话>
- INPUT：<输入>
- OUTPUT：<交付物路径>
- ALLOWED FILES：<允许新建/修改的具体文件>
- FORBIDDEN：<本任务明确禁止触碰的文件/系统>
- 被审/被改文件的版本行：<逐字抄录，例如 04_COLOR_SYSTEM.md 的「版本 **v0.1.3**」>
- STORAGE CHECK：<见 01_STORAGE_RULES §7>
- 验收条件：<见 10_ACCEPTANCE_STANDARD>
- 测试方法：<见 09_TEST_STANDARD>
```

> **版本行不是形式主义（2026-10-03 教训）**：Codex 第二轮视觉审查读取的是 `04` 的 **v0.1.1 快照**，
> 而当时磁盘上已是 v0.1.2 —— 结果 5 项 blocking 里有 3 项是**已经修完的问题**，白耗一轮。
> 从那以后：**任何审查/修改类任务，必须在 CONSTRAINT CHECK 里抄下被审文件的版本行**；
> 若抄不出或与预期不符，先停下来确认磁盘版本，不要开审。

**没有 CONSTRAINT CHECK 的实现一律不接受。**

## 4. 文件所有权与并发

- 同一时刻**只允许一个 Agent 修改同一文件**。
- DSH 派发任务时必须写明 `ALLOWED FILES`；两个并行任务的文件集**不得相交**。
- 若发现文件冲突风险 → DSH 必须串行化任务。
- Agent 不得修改 `ALLOWED FILES` 之外的文件；确有必要时先向 DSH 申请。

### 4.1 宽通配的 `ALLOWED FILES` 视为相交（v0.1.2，2026-10-03 事故后新增）

**实例**：S1-09（REWARD）在跑时，DSH 又派了 S1-08 的状态带修订。两者的 `ALLOWED FILES` 都写了
`tests/**` —— 按本节「两个并行任务的文件集不得相交」的字面规则，**这已经是一次违规派发**。
实际重叠概率低（一个改 `scenes/reward`，一个改 `scenes/combat`），但**它们写的是同一个工作树、同一个 git index**。

**因此**：

1. **宽通配（`tests/**`、`scripts/ui/**`、`scenes/**`）在并发布局中一律视为相交**。
   派发修复类任务时，`ALLOWED FILES` 必须**逐一列到具体文件**，例如
   `tests/unit/combat_probe.gd` · `tests/integration/combat_smoke.gd` · `scenes/combat/combat.tscn`，
   而不是 `tests/**`。
2. 两个 Agent 同时写**同一工作树**时，即使文件不重叠，`git add` / `git commit` 也会争用 **index 锁**
   —— 失败是「`Unable to create index.lock`」这类可恢复错误，不会损坏仓库，但会让某一批的提交失败。
   **DSH 必须在复审时核对两个并行批次的提交文件清单是否真的零重叠。**
3. 若列不出具体文件、或确实需要同一批文件 → **串行化**：把后一批建为 `backlog`，等前一批交付后再 `todo` 提起。


## 5. 禁止擅自扩大范围

任何 Agent 禁止「顺便做了……」：

```
顺便加商店 · 顺便加剧情 · 顺便加角色培养 · 顺便加联网
顺便做账号 · 顺便做每日任务 · 顺便重做 UI · 顺便新建一个系统
```

范围由 DSH 管理。发现越界改动 → DSH 必须要求回滚。

```

2. DSH 主控总提示词
3. 项目约束文档（docs/00~10）

## 8. 违规处理

| 违规 | 处理 |
|---|---|
| 无 CONSTRAINT CHECK 开工 | 产出作废，重做 |
| 修改 ALLOWED FILES 之外的文件 | 回滚，说明原因 |
| 素材未经批准进游戏 | 立即移除，记入 `12_CHANGELOG.md` |
| 向 C 盘写入项目内容 | 立即停止该工具，按 `01_STORAGE_RULES` §6 上报 |

| 宣称完成但无测试 | 视为未完成 |

## 9. 上游依赖缺失时

- 若依赖的规范/数据尚未就绪 → **不得自行发明**，向 DSH 报告并等待。
- 任何 Agent 不得边开发边创造项目标准。
## 10. 自主执行模型与关键门禁（v0.1.1 新增）

> 来源：用户《DSH 连续自主执行规则》。**本节效力等同用户直接指令**，任何 Agent、任何任务不得绕过。

### 10.1 工作模式

本项目采用 **持续自主推进 + 关键门禁人工审批**。

角色定位：

- **用户** = 产品负责人 + 最终审批者
- **DSH** = 持续运行的项目主控
- **Codex** = 视觉生产 Agent
- **Claude** = Godot 主开发 Agent

**DSH 不得因为普通实现细节频繁停止工作等待用户指令，也不得要求用户逐任务下达「继续」。**
DSH 的目标不是等待用户派任务，而是在既定方向内主动把项目推进到可交付成品。

### 10.2 DSH 的默认继续执行权（无需询问用户）

```
任务拆解 · Codex/Claude 任务派发 · Bug 修复 · 自动测试 · 单元测试 · 集成测试
Godot 场景连接 · Resource 数据整理 · 代码重构 · 性能优化 · 目录整理
Git 提交 · 文档更新 · Task Board 更新
已明确规范范围内的 UI 实现 · 已明确规范范围内的数值微调
已批准视觉方案的后续同风格资产生产 · 已批准美术素材的游戏集成
构建测试版本 · Web / Windows 测试导出 · 开发过程中发现的明确技术错误
```

结果不符合验收标准时，DSH 自行闭环，**不得每发现一个 Bug 就询问用户**：

```
发现问题 → 定位原因 → 派发修复 → 重新测试 → 再次评审 → 直到 PASS
```

### 10.3 允许自动发生的协作闭环

**开发闭环**

```
DSH → 派发 Claude → Claude 开发 → 测试 → DSH 评审
   ↓ FAIL
DSH → 分析原因 → 重新派发 Claude → 修复 → 测试 → 重新评审 → 直到 PASS
```

**美术闭环**

```
DSH → 派发 Codex → Codex 制作 → DSH 规范预审
```

若仅违反 **尺寸 / 文件命名 / Palette / 像素规格 / 导出格式 / 技术规范**，
DSH **可直接打回 Codex 修改，不需要用户介入**。

### 10.4 关键门禁（GATE 1–10）—— 只有这些必须找用户

| GATE | 触发条件 | 动作 |
|---|---|---|
| **GATE 1** | Stage 0 项目基础规范首次完成 | 暂停，向用户汇报并请求批准 |
| **GATE 2** | 涉及核心玩法方向的新增、删除或重大修改 | 暂停，请求用户裁定 |
| **GATE 3** | 涉及三张参考图所确定的整体视觉方向变化 | 暂停，请求用户裁定 |
| **GATE 4** | Codex 创建新的正式视觉方案，需要最终视觉审批 | 暂停，提交用户审批 |
| **GATE 5** | 存在两个或以上都合理、但会明显改变最终游戏体验的方案 | 暂停，请用户在方案间选择 |
| **GATE 6** | 需要新增付费软件 / 付费插件 / 外部商业服务 / 新技术栈 | 暂停，请求用户授权 |
| **GATE 7** | 发现项目相关工具无法避免写入 C 盘 | **立即停止该工具**，按 `01_STORAGE_RULES` §6 上报 |
| **GATE 8** | 需要大规模删除 / 不可逆覆盖 / 数据迁移 / 重大架构推翻 | 暂停，请求用户授权 |
| **GATE 9** | 每个主要 Milestone 完成并形成新的可试玩版本 | 暂停，交用户试玩验收 |
| **GATE 10** | 最终 Release Candidate 完成 | 暂停，交用户终验 |

**门禁一旦触发，未获用户裁定前不得开始会受其影响的工作。**

当前状态见 `11_TASK_BOARD.md` §2.1。

### 10.5 美术审批的特殊规则

新的正式视觉方向**仍然必须**经用户审批。

但用户一旦批准了某套体系（UI 风格 / 按钮体系 / Panel 体系 / 某类敌人风格 / 某类节点风格 / 某套特效风格），
Codex 后续制作**明显属于同一批准体系**的常规扩展素材时：

- **DSH 可自行批量组织生产**；
- **在里程碑或合理批次统一向用户展示**；
- **不得每生成一个 16×16 图标就中断用户**。

仍必须**单独审批**的：角色主设计 · Boss · 重要场景 · 核心 UI 页面 · 整体风格变化。

与 `07_ASSET_PIPELINE.md` 的关系：§1 的 `pending → final → 用户批准 → approved → 集成` 流程**不变**，
批量生产改变的是「多久向用户集中展示一次」，不是「能否跳过用户批准」。未获批准的素材永远不得进入 `_approved/`。

### 10.6 禁止「假完成」

**代码已生成 ≠ 完成。** 只有同时满足以下全部条件，才能标记 `DONE`：

```
代码完成 + 测试通过 + 实际场景运行 + 没有阻塞性错误 + 符合项目约束 + 达到 Acceptance Criteria
```

对应 `09_TEST_STANDARD.md` §5 与 `10_ACCEPTANCE_STANDARD.md` §3。

### 10.7 与 DSH「不抢开发」原则的关系

本节扩大的是 DSH 的**决策与推进权**，不是**开发权**。

`08_AGENT_RULES.md` §1.1 与 §2 仍然有效：**DSH 不作为正式代码开发者**，代码归 Claude、美术归 Codex。
DSH 自行推进的正确形式是「拆解 → 派发 → 评审 → 打回 → 再派发」，而不是自己写游戏代码。

## 11. EXTERNAL RESEARCH GATE（v0.1.3 新增）

**触发条件**：项目开发过程中遇到以下类型的问题时，

- Godot 引擎错误
- 原生崩溃
- 导出失败
- Vulkan / OpenGL / Web 问题
- Windows 系统错误
- API 行为异常
- Godot 版本兼容问题
- GDScript 异常行为
- 已知引擎 Bug
- 工具链错误
- 驱动相关问题
- 第三方工具异常
- 无法解释的性能问题
- 测试结果与预期不符

**任何 Agent 不得第一时间自行猜测、造轮子或直接修改架构。必须先执行一次 EXTERNAL RESEARCH GATE。**
该门禁与 §10.4 的 GATE 1–10 并行存在：GATE 决定「是否找用户」，本门禁决定「动手前是否已核对公开资料」。

### 11.1 优先联网检索（原 §一）

先搜索公开资料，确认：

1. 该问题是否已经有人遇到；
2. 是否属于当前 Godot 版本的已知 Bug；
3. 官方是否已有修复；
4. 新版本 / patch 是否已经解决；
5. 是否存在官方推荐 workaround；
6. 是否与操作系统、显卡驱动、导出模板等环境有关。

### 11.2 搜索源优先级（原 §二）

**第一优先级**（Godot 官方）：官方文档 · GitHub Issues · GitHub Pull Requests ·
Release Notes / Changelog · 官方论坛 / 官方公告。

**第二优先级**：Microsoft 官方文档 · AMD / NVIDIA / Intel 官方资料 · 浏览器官方文档 ·
Python / Git 等工具的官方文档。

**第三优先级**：Stack Overflow · Godot Forum · GitHub Discussions · Reddit 等社区。

**社区结论只能作为线索。不得把论坛中的单个回答直接视为事实。**

### 11.3 必须带版本搜索（原 §三）

涉及 Godot 时，查询必须优先包含当前版本，例如 `Godot 4.7.1 stable`：
`Godot 4.7.1 DirAccess crash Windows` · `Godot 4.7.1 log open access violation` · `Godot 4.7.1 0xc0000005`。
找不到再逐级扩大到 `Godot 4.7` → `Godot 4.x`。**不得一开始就拿 Godot 3.x 的方案套用。**

### 11.4 搜索结果必须验证适用性（原 §四）

发现解决方案后必须确认：针对哪个 Godot 版本 · 哪个操作系统 · 是否已过时 ·
是否只是临时 workaround · 是否会影响当前项目架构 · **是否违反 C 盘禁令** ·
**是否需要管理员权限** · **是否需要新增工具** · **是否会修改系统设置**。

不能因为「网上有人这么做」就直接执行。

### 11.5 优先复用成熟方案（原 §五）

如果官方或社区已有成熟可靠的解决方案，**优先采用成熟方案**。不要重新发明：
dump 工具 · 日志工具 · 导出脚本 · workaround · 自定义启动器 · 自定义补丁。

除非：1) 没有可靠现成方案；2) 现有方案不适用于当前项目；3) 自研方案确实明显更简单。

### 11.6 搜索后再做最小复现（原 §六）

正确顺序：

```
问题出现 → 保存现场 → 联网搜索类似案例 → 确认已知问题 / 官方行为
        → 建立最小复现 → 与公开案例对照 → 确定根因范围
        → 提出方案 → 测试方案 → 再实施
```

不要反过来：先大改项目，然后再搜为什么。

### 11.7 搜索结果汇报格式（原 §七，**强制**）

涉及重要问题时，必须向用户或任务卡记录以下八项：

```
## 问题
实际现象。

## 搜索关键词
使用过的主要查询。

## 找到的资料
至少列出重要来源及结论。

## 官方是否已知
YES / NO / UNKNOWN。

## 与本项目是否匹配
说明版本、平台和触发条件是否一致。

## 可用解决方案
方案 A / B / C。

## 推荐方案
说明理由。

## 风险
例如：管理员权限 · 系统修改 · C 盘写入 · 数据风险 · 兼容性影响。
```

> **「官方是否已知」必须落到可核对的出处**（issue 号 / milestone / changelog 条目 / PR 号 / commit SHA），
> 不接受「官方好像知道」。**「issue 仍开着」不等于「未修」** —— 修复提交若未在 message 里引用 issue 号，
> GitHub 不会自动关联，issue 会一直开着（2026-10-04 PET-60 实证）。

### 11.8 严禁搜索结果污染项目（原 §八）

搜索网页时**不得**：下载来历不明 EXE · 执行未知 PowerShell 脚本 · 下载未知 DLL ·
关闭系统安全设置 · 修改注册表后不记录 · 将用户隐私日志直接上传到公开平台。
需要下载工具时**优先官方来源**。

### 11.9 涉及项目日志的隐私规则（原 §九）

向搜索引擎、论坛或公开 Issue 提交内容之前，必须检查并去掉：
**用户名 · 个人目录 · Token · API Key · 密码 · Cookie · 私有仓库地址 · 其他敏感信息**。
**本地分析不受此限制。**

### 11.10 当前 [PET-60] 应用本规则（原 §十）

对于当前 Godot 4.7.1 的 `0xc0000005` 以及 `DirAccess / log-open` 相关崩溃调查，
应优先联网搜索 Godot GitHub Issues / 4.7.1 changelog / 相关 PR，以及 Windows 上
`DirAccess` / `FileAccess` / log path 的已知问题，并判断：

- 是否已有上游 issue；
- 是否已在 newer build 修复；
- 是否存在官方 workaround；
- `core/io/dir_access.cpp` 对应代码行为；
- fault offset 是否能与公开符号 / 源码定位对应。
