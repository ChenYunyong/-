> 状态：`FROZEN-DRAFT`（待用户批准）｜版本 **v0.1.7**｜维护者 DSH

## 1. 测试层级

| 层级 | 位置 | 说明 | 触发 |
|---|---|---|---|
| 单元测试 | `tests/unit/` | 纯函数 / 数据类 / 图算法（蓝图拓扑、Heat 计算、奖励池） | 每次提交 |
| 集成测试 | `tests/integration/` | 状态机流转、蓝图→战斗一局的完整链路 | 每完成一个系统 |
| 场景冒烟 | `tests/output/` | 每个 `.tscn` 能否独立实例化、无报错 | 每完成一个场景 |
| 手动验收 | 编辑器 + 导出包 | 双端输入、视觉、手感 | 每阶段 |
| 回归 | 全量 | 修复 bug 后必须补一条回归用例 | 每次修复 |

测试输出（日志、截图、报告）一律写入：

```
D:\GameDev\PixelFusion\tests\output
```

### 1.1 分级执行（L1 / L2 / L3，v0.1.7 新增）

用户 2026-10-04 指令：**禁止每个小改动都跑整个大型测试集。**

| 级别 | 何时跑 | 内容 | 目标时长 |
|---|---|---|---|
| **L1 开发任务** | 每次小改动 / 每张普通任务卡 | 当前模块单元测试 + 当前场景冒烟 + 直接依赖 | 数十秒 ~ 数分钟 |
| **L2 阶段集成** | 完成一个明显功能块 | 核心 unit + integration + 相关 smoke | 数分钟 |
| **L3 完整基线** | 里程碑 / 引擎升级 / 核心架构改动 / RC / 用户验收前 | 全量 unit + integration + 全部冒烟 + 产物 + 像素探针 | 长 |

- **普通任务卡的默认是 L1，不是 L3。** 需要 L2 / L3 时由 DSH 在派卡时**写明**；没写就按 L1 执行。
- 卡上写 L1 时，**不要求**「全量基线数字不得退化」的对照，只要求**本模块不退化**。
- 禁止把「1000+ 单元测试 + 全场景 + Web Export + Render Probe」当普通卡默认流程。

## 2. 必须验证的场景（每个功能至少覆盖）

```
1. 正常路径
2. 边界条件
3. 重复操作
4. 状态切换
5. 空数据
6. 非法输入
7. 重新进入场景
8. 重新开始游戏
9. 中途退出 / 返回主菜单
```

## 3. 各系统的必测点

### 3.1 状态机（Stage 1）
- PREPARATION 停留 10 分钟 → 不自动进入 COMBAT。
- 连续快速点击「开始战斗」→ 只切换一次（防重入）。
- COMBAT → REWARD → PREPARATION 循环 10 次无内存/节点泄漏。
- 任意状态下退出到主菜单 → 无残留。

### 3.2 蓝图（Stage 2）
- 空蓝图进入战斗 → 不崩溃，有明确提示。
- 删除正在被引用的节点 → 连线一并清理。
- 环路连接 → 检测并提示，不死循环。
- 悬空端口 / 类型不匹配 → 拒绝连接或明确提示。
- 保存后重载 → 结构完全一致。

### 3.3 信号传播（Stage 3）
- 同一蓝图 + 同一输入 → 结果完全一致（确定性）。
- 执行顺序稳定（多次运行顺序一致）。
- 断开子图不参与执行。

### 3.4 战斗（Stage 4）
- Heat 达到阈值 → Overheat 触发且只触发一次。
- 波次清空 → REWARD 恰好进入一次。
- CORE 被摧毁 → RESULT。
- 0 敌人 / 1 敌人 / 大量敌人。
- 倍速切换不改变结算结果。

## 4. 测试编写规则

- 测试文件命名 `test_<被测对象>.gd`，放在对应层级目录。
- 每个测试必须能独立运行，不依赖执行顺序。
- 禁止依赖真实时间（用固定 tick / 注入时钟）。
- 禁止依赖真实随机（用固定 seed 的 RNG）。
- 禁止用 `print` 当作断言；必须有明确 pass/fail。
- 测试数据不得污染正式 `data/`，用测试专用 `.tres` 或代码构造。
- **禁止用「配置项等于某个值」代替「可见结果确实出现」**（v0.1.1，2026-10-03 实例）：
  规范若要求某个**视觉结果**（阴影 / 描边 / 高光是否存在、是否模糊），
  至少要有**一条像素级或渲染产物证据**证明它真的被绘制出来。
  只断言字段值不算 —— 实例：`shadow_size = 0` 时字段断言全绿，而阴影**一个像素都没画**，
  等于「断言了一个空实现」。取像素需真实渲染路径（`--headless` 的 dummy 驱动不产像素）。
- **像素探针的常驻编排**（v0.1.2）：光有上一条规则不够 —— 没有「谁在什么时候跑」的约定，规则会**静默腐烂**
  （2026-10-03 的教训：探针首版自身坐标写错，字段层 390 条断言全绿，**只有像素图暴露了问题**）。
  - **触发条件**：任何改动 **Theme / StyleBox / 视觉 Token** 的批次，
    以及任何**要宣称「某个视觉结果已实现」**的批次 —— 在常规 `--headless` 回归之外**必须**再跑像素探针。
  - **探针刻意不进** `run_tests.gd`：它需要真实渲染上下文，`--headless` 的 dummy 驱动不产像素。
  - **探针必须自证判别力**：每条断言都要能被一次「故意改坏」的反向对照打红；只写正面断言不算数。
  - **执行者**：改动视觉的 Agent 在 L1 自测时必须跑，并把像素输出贴回；DSH 在 L2 审查时核对。
  - **命令**（逐条跑，**不加** `--headless`）：

    ```
    tools\godot\Godot_v4.7.1-stable_win64_console.exe --path D:\GameDev\PixelFusion --script res://tests/unit/run_render_probes.gd
    ```

- **新增 `class_name` / 新脚本后，验证前必须先刷新全局类缓存**（v0.1.4，2026-10-03 实例 —— 差点造成误打回）：
  Godot 把 `class_name` 的全局注册落在 **`.godot/global_script_class_cache.cfg`**，而 `.godot/` 被 gitignore。
  这份缓存**不会**因为 `git checkout` / `cherry-pick` 拉进新脚本而自动更新 —— 于是新增一个带 `class_name` 的文件、
  并让既有脚本 `extends` 它之后，**在工作树里直接跑测试会全线炸**：
  `SCRIPT ERROR: Parse Error: Could not find base class "X"` → 脚本加载失败 → 场景 `_ready()` 不跑 →
  冒烟用例**总数骤降**、探针大面积失败。**这是环境假红，不是代码缺陷。**
  - **验证任何「新增了带 `class_name` 的文件」的批次之前，先跑一次**：

    ```
    tools\godot\Godot_v4.7.1-stable_win64_console.exe --headless --path D:\GameDev\PixelFusion --import
    ```

    然后确认缓存里**已出现新类名**：`Select-String .godot\global_script_class_cache.cfg -Pattern '<类名>'`。
  - **判别特征**：失败面「大得不合理」（例如 6/6 场景冒烟全红，且**总断言数骤降**而非个别断言变红），
    且日志里有 `Could not find base class` —— 先怀疑缓存，**别急着打回**。
  - **反向纪律**：打回前必须确认**同一命令在同一棵树上、该改动之前是绿的**（受控对照）。
    没有这个对照，就无法区分「被测改动导致」与「环境导致」。
  - **`.gd.uid` 必须随提交入库**：新脚本导入时 Godot 会生成 `<脚本>.gd.uid`；本仓库既有 52 个 `.uid` 已入库，
    新脚本的 `.uid` 一并提交，保证新旧脚本约定一致、UID 不因再次导入而漂移。

- **在仓库上跑过 `--editor` 之后，必须 `git diff project.godot` 确认**（v0.1.6，2026-10-03 实例）：
  Godot 编辑器**打开项目**时会**重写 `project.godot`** —— 官方样板注释会覆盖项目自己的注释，
  并且会**静默丢掉它不认识的键**。实测本仓库被丢掉过 `window/stretch/aspect="keep"`（属 `06 §1` 的整数缩放配置）。
  - **首选做法**：把编辑器测试跑在**项目副本**上（如 `D:\Temp\PixelFusion\<task>\projcopy\`），不要跑在仓库上。
  - 若必须跑在仓库上：跑完立刻 `git diff project.godot`；有改动就 `git checkout -- project.godot` 还原，
    并核对 `window/stretch/aspect="keep"` 是否还在。
  - 这条同样适用于**无参数的裸启动**（项目管理器）—— 它一样会改写被打开工程的文件。

## 5. 完成定义（Definition of Done）

一个任务只有同时满足以下条件才算完成：

```
[ ] 代码符合 02_CODE_STANDARD
[ ] 只修改了 ALLOWED FILES
[ ] 所有新增/修改逻辑有对应测试
[ ] 测试在本机实际运行过，并贴出结果
[ ] §2 的九类场景中适用的都已覆盖
[ ] 无 Godot 报错 / 无 warning 新增 —— **例外（v0.1.5）**：由**被断言的负路径用例**主动触发、
      且在报告里**逐条点名**的报错 / warning **不算新增**（§4 本来就要求写反向对照、故意走错误分支；
      不设例外，§4 与 §5 会互相打架）。除此之外的增量必须清零：**ERROR 计数应与基线相同**，
      WARNING 增量必须逐条归因，说不出出处的一律算新增。
[ ] **退出期资源清点（v0.1.7 新增）**：`N resources still in use at exit` / `N ObjectDB instances were leaked at exit`
      单列为一项，必须**如实报告并逐条归因**。判定规则：
      - 泄漏对象**不在本批 ALLOWED FILES 内**、且能在**未改动的基线**上以等价条件复现 ⇒ **不判本批未达 DoD**，
        但由 DSH 登记为独立缺陷（**不得静默豁免**）；
      - 泄漏对象属于本批文件，或基线无法复现 ⇒ **算真实回归**，本批未达 DoD。
[ ] 未越界引入范围外功能
[ ] 已更新 12_CHANGELOG.md（由 DSH 执行）
```
